## Gesture implementation

The one-finger right-edge scrolling strip occupies 12% of the width (starts at 88%). Drawing and touch/tap eligibility share that boundary. Its scroll speed, fractional accumulation and first-contact mode locking are unchanged; the two-finger classifier does not depend on the strip boundary.

`PinchGesture` sorts contacts by pointer ID and compares displacement from their shared starting baseline. Pinch needs at least 12 dp of spacing change, spacing change more than 1.8 times centroid translation, and opposing or stationary relative finger movement. Scroll needs at least 8 dp of centroid translation dominant over spacing change by the same ratio. Ambiguous motion waits rather than producing zoom. Classification then remains locked while the same two pointers are present. This dominance gap provides hysteresis; classification does not flip on direction reversals.

Pinch converts 32 dp of spacing change to one signed zoom step, accumulating fractional changes. Outward is positive; inward negative. TouchpadView uses ZoomPacer: one step at most every 30 ms, immediately at the next display frame when first ready, with at most four waiting steps. Fast motion coalesces excess steps instead of producing multi-tick wheel bursts or a long catch-up queue. Reversal replaces queued old-direction steps. The 32 dp scale and fractional accumulation remain unchanged; very fast gestures intentionally do not preserve every requested step. Pending zoom is discarded on finger lift/cancel, disabling, detach or physical-button interruption. After a pinch loses a finger, the remaining contact cannot jump the cursor or start a new pinch until all fingers lift. Small unclassified two-finger taps retain right-click behavior. Both ordinary scroll methods and mouse gesture/math implementations remain available. Physical mouse holds suppress pinch.

## Host selection and reports

Settings adds persistent `host_os` in the existing touchpad preferences. Unknown/missing values default to Windows / Linux; sensitivity storage is unchanged. There is no OS autodetection.

- Windows / Linux: keyboard ID 1 Ctrl-down (8 bytes), mouse ID 2 signed wheel (4 bytes), keyboard ID 1 neutral. Normal scroll never adds Ctrl.
- macOS: Command+Shift+Equals for US `+`, or Command+Minus, followed immediately by a neutral keyboard report. Each step is one press/release pair. No modified mouse wheel is used for macOS.

The existing descriptor, IDs, payload sizes and Bluetooth registration/connection logic are unchanged. `HidManager.zoom` runs a whole sequence on the existing serial worker, so queued typing/mouse operations cannot interleave between modifier press and release. It does not mutate the user's KeyboardState. Zoom is skipped while any user keyboard key/modifier or mouse button is held, or in boot protocol/disconnected state. This conservative rule avoids shortcut collisions but means pinch with a sticky toolbar modifier is intentionally ignored. Successful IME taps finish their down/up pair on that same worker before another task runs.

On transmission rejection, existing recovery clears both input states, attempts neutral reports and disconnects; remaining zoom reports stop. Runtime exceptions use existing close/cleanup. Each successful zoom step ends neutral, so cancellation between frames has no gesture-owned modifier to release. Radio loss/process termination cannot guarantee release delivery; the host must handle disconnect and each new connection starts neutral.

## Compatibility limits

These are application shortcuts, not a native precision-touchpad multitouch protocol. Ctrl+wheel depends on the focused application; some editors, terminals and desktop bindings may ignore it or use it for something else. Command+Plus/Minus depends on application support and host layout; Finder, games, custom shortcuts and non-US layouts may behave differently. The US HID mapping cannot produce a portable Plus symbol on every international layout. Select US host layout for initial macOS validation. Safari/Chromium-style page zoom is a suitable initial target; other applications must be tested separately. Existing IME Unicode/Bangla limitations remain. No platform is certified by unit tests.

Apple documents Command+Plus/Minus for Safari website zoom: [Safari shortcuts](https://support.apple.com/en-gb/guide/safari/cpsh003/mac). This documents the intended shortcut, not BluePad interoperability.

## Gesture refinement

The previous tap state machine sent the first click before knowing whether a second touch would become a drag. The subsequent held press could therefore be interpreted by a desktop title bar as the second press of a double-click. Single clicks now wait for a bounded 120 ms recognition window (or the configured double-tap timeout if shorter). A nearby second touch inside this window consumes the pending first click: a quick release sends two complete clicks, whereas a hold/movement sends only one held button-down and releases on lift/cancel. A timer handles stationary holds and single-tap expiry; a late timer cannot turn a held second touch into double-click. Dedicated physical buttons remain immediate.

Real-device retest: on an Ubuntu window title bar, repeat quick double-clicks (maximize/restore), then double-tap with second touch held and move (drag without maximize). Test movement before the hold deadline, a stationary hold, long first touch, cancelled second touch, Home/lock/disconnect, and dedicated-button dragging. Judge the 120 ms single-tap tradeoff and the shorter double-tap recognition window explicitly. For zoom, compare slow fractional pinches, fast large pinches, repeated reversals and immediate cancellation: no multi-step bursts or stale catch-up should occur. Application zoom remains discrete; this does not implement native continuous zoom, and Bluetooth host delivery/latency still requires hardware evidence.

## Failed-test timing audit

The previous 180 ms first-tap delay was intentional but noticeable. A separate defect in usability was the Android tap timeout (~100 ms) being used as the stationary second-touch hold deadline: a normal second tap lasting 100–180 ms could become a drag. Also, double-click output was four back-to-back HID changes with no deliberate edge spacing. The revised UI uses 120 ms single-tap deferral, 180 ms stationary hold recognition, and 20 ms click-edge spacing. A recognized double-click sends down/up/down/up over nominally 60 ms. Movement-triggered dragging still starts immediately after crossing slop; its first tap is consumed. Two taps outside the recognizer's 120 ms gap become two paced single clicks, whose interpretation then depends on the host double-click settings. The first-tap ambiguity cannot be removed while guaranteeing that drag initiation sends no first click. Late click timers send one edge and schedule the next relative to actual execution, rather than flushing all four at once. Cancellation releases any active paced click and discards scheduled edges.

Zoom pacing changed from 60 ms/two waiting steps to 30 ms/four waiting steps, preserving one step per dispatch and the 32 dp quantum. This halves the added pacing interval and reduces clipping of moderately fast pinches. Extremely fast pinches still coalesce excess steps. A first zoom step still requires 32 dp of spacing change, after classification at 12 dp. Slow movement can therefore take time to reach a discrete application zoom increment; sensitivity was not increased to conceal this limitation. No deliberate sleeps were found in modifier transmission. Host/transport latency is not established: opt-in HID logs now include `queueMs` and individual `sendMs` for physical profiling. UI edge spacing does not guarantee host-delivery spacing if the Bluetooth worker or stack stalls.

Retest single taps for perceived delay; normal double-clicks with different second-touch durations and inter-tap gaps; stationary second-touch holds, early movement, browser tab/title-bar drag, rapid repeated gestures, and cancellation/disconnection while a click is down. Confirm dedicated buttons remain immediate. Compare slow/fast pinch, reversal, immediate lift, typing, scrolling and held-modifier suppression. Capture debug logs during failures, plus Ubuntu evtest timestamps for mouse button press/release spacing. Neither failed hardware test is certified repaired by these automated checks.

## Rapid double-tap endpoint audit

A focused failing test reproduced this sequence: first DOWN 0 ms / UP 30 ms, second DOWN 65 ms / UP 95 ms, with only the final UP coordinate displaced 10 dp (above the 8 dp test movement slop). TouchpadView feeds that terminal finger coordinate before feeding an empty list. Previously SECOND_TAP became DRAG from that UP sample, then immediately released; the host was offered only one click pair. The 35 ms inter-tap gap was inside the pending window, so the 120 ms deadline was not the cause of this reproduced failure.

TouchpadGestures.sample now accepts an `ending` flag, set only for the current ACTION_UP sample. Terminal lift displacement cannot initiate drag. Actual earlier MOVE displacement still does; the 180 ms hold deadline and late-timer handling remain unchanged. No thresholds or click spacing were increased. Added production-configuration tests for rapid lift jitter, moderate taps, slow two-single output, a rapid double followed immediately by movement, and live-movement/hold drag release. Timing remains 120 ms pending single, 180 ms stationary hold and 20 ms nominal click edges. HID transport and zoom pacing are unchanged.

This establishes a code defect, not proof that every observed rapid-tap failure has this cause. Natural taps that cross slop in an actual MOVE event can still be classified as dragging. Actual host press/release timing cannot be established from pure tests or send acceptance; worker/stack stalls may compress UI-scheduled edges. The existing send-duration diagnostics and Ubuntu evtest timestamps should be captured during the next test. Enable `adb shell setprop log.tag.BluePadTouch DEBUG` as well as BluePadHid DEBUG; terminal UP traces now show recognizer phase before/after endpoint processing.

## Natural second-tap jitter refinement

The shared normal movement slop was also used to acquire a second-tap drag. The earlier diagnostic test showed that 9 dp of real MOVE displacement with 8 dp slop produced one drag press/release rather than a double-click. The user's clarified hardware observation establishes that incidental second-tap movement is being mistaken for drag intent. Second-tap dragging now has a separate threshold of twice Android's density-normalized touch slop (16 dp for normal 8 dp slop). It is measured as straight-line net displacement from the second contact's initial DOWN; changing direction does not accumulate toward it. Exact-threshold movement remains a tap candidate; deliberate movement beyond it while down starts drag. Terminal UP still cannot initiate drag. The stationary hold deadline, single-tap deferral, double-click recognition window and click-edge pacing are unchanged.

Tests cover above-normal-slop incidental movement, repeated directional changes, exact drag-threshold boundary, second-contact origin rather than first-tap origin, hold after minor jitter and cancellation. Existing intentional-drag fixtures now use displacement exceeding the separate threshold; earlier rapid/moderate tap, terminal-UP, single-click, dedicated-button, zoom, scroll and HID cleanup tests remain in the suite. The diagnostic note below the earlier audit is historical: `slop_crossed` alone no longer classifies a second-tap drag; look for `drag_slop_crossed` at the separate threshold or `drag_classified` from the unchanged hold deadline.

Retest natural fast and moderate double-taps with light finger drift and direction changes, then deliberate double-tap dragging and stationary holding. Verify title-bar maximize/restore only on a released double-tap, browser-tab dragging, cancel/lift/disconnect cleanup and dedicated-button dragging. This change deliberately requires more movement to acquire a drag before the hold deadline; it does not change cursor sensitivity. Hardware confirmation is still required.

## Captured-log pacing defect and repair

The 10,580,030-byte `/tmp/bluepad-fast-tap-android.log` was inspected. In process 24406 at 06:42:38.496 (lines 86205–86222), `double_recognized` is followed by a first press at actual uptime 144687521, while its next deadline is 144687523: that deadline came from the older UP event time 144687503 plus the configured 20 ms. Release ran at actual uptime 144687524, only 3 ms after press; HID submission sequence 138/139 began at 144687523/144687529, 6 ms apart. Both requests were accepted with mouse masks 1 then 0. Across 18 complete recognized-double traces from that process, first UI press lengths were 4–17 ms rather than the intended 20 ms. A separate complete 34 ms second-tap example at 06:44:18.121 submitted sequence 868–871 as masks 1,0,1,0, all accepted, with submission times 144787151/144787159/144787179/144787199. These examples establish compressed initial pulse timing; they do not establish host receipt or identify which unlabeled trial failed visibly.

The demonstrated code defect is using MotionEvent sampling time to pace reports emitted later on the main thread. Recognition must use event time, but output deadlines must use actual dispatch uptime. TouchpadGestures now accepts an injected report clock, wired to SystemClock.uptimeMillis in TouchpadView. Initial click scheduling and subsequent edge deadlines use that clock; the next deadline is computed after emitting the preceding edge. Late callback handling still emits one edge without catch-up bursts. No 20 ms interval, tap/hold timeout, drag threshold, zoom or HID report format was changed. Tests inject stale event times, slow callbacks and late timers and prove distinct press/release spacing. Debug traces retain event time separately from dispatch time.

The earlier time-matrix tests used one clock for both event generation and dispatch and therefore missed this defect. Existing cancellations, holds, browser dragging and dedicated buttons remain covered. A corrected UI schedule cannot guarantee Bluetooth-worker or host spacing under arbitrary stack stalls; retest with a fresh short Android capture and the existing Ubuntu evtest procedure. Record one failed fast trial and one passed moderate trial explicitly so host interpretation can be correlated. Do not infer that missing log lines in this long multi-session capture mean reports were lost, nor that API acceptance proves host delivery.
